# Нарезка комментариев и эмбеддинги: результаты замеров

> **Что принято после этого отчёта (2026-10-09).** Рабочая модель —
> `intfloat/multilingual-e5-small`, 384 измерения: сравнение четырёх моделей в
> [embedding-model-benchmark.md](embedding-model-benchmark.md) не показало
> преимущества базовой. Рабочая нарезка — `token_budget`, 256 токенов, внутри
> канала, **без перекрытия**: прирост от перекрытия 10 % не вышел за шум. Хранятся
> оба уровня. Замеры ниже выполнены на `multilingual-e5-base` и оставлены как
> были; там, где текст называет базовую модель выбранной или рекомендует
> перекрытие, действует это примечание.

Дата замеров: 2026-10-08. Все числа получены командами из раздела
«Как повторить» на данных, собранных в PostgreSQL.

## Короткие ответы

| Вопрос | Ответ |
|---|---|
| Нужны ли эмбеддинги отдельных сообщений? | Да. При равном объёме выдачи они дают самый плотный результат: 76 % выданных токенов относятся к теме, и 16,4 % всех релевантных сообщений помещаются в 1000 токенов. |
| Нужны ли эмбеддинги чанков? | Да, как второй уровень. Сами по себе чанки точнее попадают первым результатом (MRR до 0,94 против 0,81), но доля текста по теме в их выдаче вдвое-втрое ниже: 24–38 % против 76 %. |
| Хранить оба уровня? | Да. Ранжирование сообщений с учётом лучшего чанка, в который они входят, сохраняет плотность уровня сообщений и поднимает MRR с 0,81 до 0,89. |
| Какая нарезка лучшая для поиска? | Единственной нет: это зависит от того, что считать успехом. Для второго уровня — бюджет 256 токенов внутри канала с перекрытием 10 %. |
| Какая лучше для подготовки контекста LLM? | Сообщения, ранжированные с учётом чанков. Крупные чанки проигрывают: в 1000 токенов помещается 4–7 % релевантного против 14–16 %. |
| Нужны ли границы каналов? | На качество поиска они не влияют: разница в пределах шума. Оставлять их стоит ради смысла чанка: без границ до 67 % чанков склеены из разных обсуждений. |
| Оптимальный бюджет токенов? | 256. При 128 выигрыш в попадании первым результатом меньше, при 512 выдача слишком разбавлена. |
| Нужно ли перекрытие? | 10 % даёт небольшой прирост при цене +3,5 % векторов; 20 % прироста не даёт. Разница близка к шуму замеров. |
| Что делать с очень короткими ответами? | Не искать по ним отдельно. Сообщения короче 5 токенов — четверть всех, но 2,7 % текста; в поиске они занимают 9 % верхних мест, не неся содержания. Их место — внутри чанка. |
| Отдельные чанки для разных временных контекстов? | Окно по времени без ограничения размера не годится: чанки вырастают до 128 тысяч токенов, до 19 % обрезается моделью. Пауза как дополнительная граница при ограниченном размере допустима, но выигрыша в поиске не показала. |

Рабочая стратегия нарезки этим документом **не внедрена**: в коде нет стратегии
по умолчанию, чанки строятся только явной командой. Рекомендация — в разделе
«Вывод».

## Данные

Комментарии 15 профилей — пользователей, по которым собрана вся история
комментариев. Шестнадцатый профиль пуст.

- 44 314 комментариев в 54 каналах.
- Распределение неравномерно: у одного пользователя 24 076 комментариев, у
  следующих 8 936, 5 364, 1 797 и 1 609, у остальных меньше 800.
- Текст в том виде, в каком он пришёл из Telegram.

Всего в базе 110 585 комментариев, но остальные принадлежат авторам, у которых
собрано по нескольку сообщений; анализ профиля для них не имеет смысла.

### Очень короткие сообщения

Сообщений короче 5 токенов 10 659, различных текстов среди них 5 834. Самые
частые — служебные реплики без собственного содержания: «да» (421 раз), «нет»
(201), «привет» (107), «лол» (102), «+» (69), «и?» (44), «понял» (43), «ок» (30),
«конечно» (28), «?» (22), а также команды модерации чата и приветствия.

Отдельный вектор такого сообщения описывает слово, а не высказывание: о чём «да»,
из него не узнать. При этом модель считает такие реплики близкими почти к любому
запросу: в пробной проверке «да» оказалось ближе к запросу о профсоюзах, чем
предложение о погоде.

## Модель

Размерность вектора задаёт модель, а не размер чанка: у каждой модели она
постоянна. Замеры нарезки выполнены одной моделью, чтобы не менять два
параметра сразу.

| Параметр | Значение |
|---|---|
| Модель | `intfloat/multilingual-e5-base` |
| Ревизия | `d128750597153bb5987e10b1c3493a34e5a4502a` |
| Токенизатор | из того же репозитория, XLM-RoBERTa SentencePiece |
| Размерность | 768 |
| Предел входа | 512 токенов, из них 508 на текст |
| Объединение токенов | среднее по маске внимания |
| Нормализация | L2 |
| Префиксы | `passage: ` для хранимого текста, `query: ` для запроса |

Так предписывает карточка модели; реализация — `embeddings/e5.py`.

Более позднее сравнение четырёх моделей, с BGE-M3 и Qwen3 и с доверительными
интервалами, — в [embedding-model-benchmark.md](embedding-model-benchmark.md); по
его итогам рекомендована малая модель E5.

- Большая модель немного лучше по MRR и по выдаче в 1000 токенов, но втрое
  медленнее базовой и требует векторов на треть длиннее.
- Малая модель на этих запросах не хуже базовой, в 2,7 раза быстрее и вдвое
  компактнее.

  вариантами нарезки. На 22 запросах доверительные интервалы не считались,
  поэтому утверждать превосходство какой-либо модели нельзя.

**Выбрана базовая модель, размерность 768.** Основания: этой же моделью и
ревизией уже считает раздел сравнения авторов, так что векторы можно будет
использовать совместно; по скорости и объёму она приемлема (842 сообщения в
секунду, 180 МБ на 44 тысячи векторов). Замеры выбор не подтверждают и не
опровергают. Если важнее скорость и объём, малая модель — равноценная замена;
менять нужно до наполнения таблиц, потому что размерность зашита в миграцию.

## Что сравнивалось

Чанк — упорядоченный список целых сообщений одного пользователя; текст чанка —
сообщения через перевод строки. Сообщение никогда не режется.

| Группа | Правило | Параметры |
|---|---|---|
| A | одно сообщение — один вектор | – |
| A, без коротких | то же, но сообщения короче порога не индексируются | порог 5 и 10 токенов |
| B | N сообщений подряд | N = 2, 3, 5, 10 |
| C | целые сообщения до бюджета токенов | 128, 256, 512; перекрытие 0, 10, 20 % |
| D | новый чанк, когда пауза достигла порога | 5 мин, 30 мин, 2 ч, сутки; размер не ограничен |
| F hybrid | пауза, бюджет токенов и число сообщений вместе | шесть сочетаний |
| F short-merge | короткие сообщения объединяются, длинные остаются отдельными | четыре сочетания |
| G | векторы сообщений и чанков вместе | два способа, четыре нарезки |

Пометка `channel` означает, что каждая лента канала нарезается отдельно и чанк не
пересекает границу канала; `global` — нарезается общая хронология пользователя.
Группа E из задания (учёт каналов) — это сравнение пар `channel` и `global`.

Два способа группы G:

- **rrf** — два списка результатов (сообщения и чанки) сливаются по обратному
  рангу; элемент, не добавляющий новых сообщений, пропускается.
- **context** — возвращаются сообщения, а оценка сообщения равна полусумме его
  собственного сходства с запросом и сходства лучшего чанка, в который оно входит.

## Как измерялось

**Набор запросов.** 22 запроса по пяти крупнейшим профилям: профсоюзы, миграция,
религия, образование, положение женщин, медицина, цены и зарплаты, капитализм,
война, Сталин, Запад, Украина, чиновники, выборы, национализм, еда, КПРФ,
работа, игры и фильмы, СССР, технологии, государство. Каждый запрос ищет только
среди комментариев своего пользователя. На запрос приходится от 17 до 305
релевантных сообщений, всего 2 669. Набор лежит в `benchmarks/eval/`; в
репозитории только текст запросов и анонимные идентификаторы.

**Релевантность** назначена сообщениям, а не чанкам:

1. сообщение релевантно, если совпадает с регулярным выражением темы — признак
   лексический, от модели не зависит;
2. прочитаны 12 лучших результатов уровня сообщений по каждому запросу, вручную
   добавлено 20 релевантных сообщений без ключевого слова и убрано одно ложное.

**Метрики.** Чанк засчитывается за те релевантные сообщения, которые он принёс
первым, поэтому варианты с разным размером чанка оцениваются по одной разметке.

| Метрика | Что показывает |
|---|---|
| R@5, R@10 | доля релевантных сообщений в первых 5 и 10 результатах |
| MRR | обратный ранг первого результата с релевантным сообщением |
| NDCG@10 | качество порядка первых 10 результатов |
| R@1000 ток. | доля релевантных сообщений в результатах, которые вместе помещаются в 1000 токенов |
| Доля релев. токенов, top-5 | какая часть токенов первых пяти результатов относится к теме |

### Ограничения

- **R@5 и R@10 растут вместе с размером чанка по построению**: десять чанков по
  двадцать сообщений содержат больше, чем десять сообщений. Они малы у всех
  вариантов, потому что релевантных сообщений десятки и сотни. Сопоставимое
  сравнение дают R@1000 ток. и доля релевантных токенов.
- **NDCG@10 между вариантами с разным размером чанка несопоставим.** Идеальная
  выдача строится для каждого варианта из его собственных чанков, и у крупных
  чанков идеал труднодостижим. Столбец приведён, выводы на нём не строятся.
- **Разметка неполная и шумная.** Совпадения с выражением целиком не
  прочитаны; совпадение значит «упоминает тему», а не «выражает позицию». Доля
  ложных совпадений не измерена; в одном запросе, прочитанном подробно, она была
  около одной пятой.
- **Ручные добавления взяты из выдачи уровня сообщений** и слегка ему подыгрывают.
- **Короткие ответы, релевантные только через контекст, не размечены.** Recall
  о них ничего не говорит; вместо этого измерена доля коротких сообщений в выдаче.
- **Запросов 22, доверительные интервалы не считались.** Разницу в одну-две
  сотых между вариантами следует считать шумом.
- **Один пользователь даёт 54 % корпуса**, но только 4 запроса из 22.

### Оператор расстояния

| Оператор | p50, мс | Тот же top-10, что у косинусного |
|---|---|---|
| `<=>` косинусное расстояние | 28,4 | – |
| `<#>` скалярное произведение | 28,2 | 100 % запросов |
| `<->` евклидово расстояние | 27,7 | 100 % запросов |

Векторы нормализованы, поэтому три оператора pgvector дают один и тот же порядок;
скорость одинакова. Выбран косинусный `<=>`: он остаётся верным, даже если в
таблицу попадёт ненормализованный вектор. Совпадение порядка проверяет тест
`test_cosine_inner_product_and_l2_rank_normalized_vectors_alike`.

## Примеры

Тексты комментариев в репозиторий не попадают, поэтому примеры описаны, а не
процитированы.

**Удачная выдача.** Запрос об отношении к трудовым мигрантам, профиль с
развёрнутыми сообщениями (медиана 32 токена). Все двенадцать первых результатов
уровня сообщений — высказывания по теме, с ключевым словом. Запрос о медицине
для того же профиля: среди первых двенадцати четыре сообщения по теме без
ключевого слова — о доступе к медицинской помощи и о лечении детей за счёт
бюджета.

**Неудачная выдача.**

- Запрос о еде и готовке, профиль-чат (медиана 5 токенов). Одиннадцать из
  двенадцати первых результатов — реплики из одного-трёх слов, не связанные с
  едой; часть попала в выдачу по созвучию со словом из запроса.
- Запросы о работе и об играх и фильмах, профиль с 1 797 сообщениями. Первые
  места занимают голые ссылки на видео и заголовки из двух-трёх слов.
- Запрос о Западе. Семь из двенадцати первых результатов без ключевого слова —
  ссылки без текста.

Общая причина: вектор очень короткого текста или ссылки мало что описывает и
оказывается близок к чему угодно. Это и есть первая из двух крайностей — слишком
маленький кусок. Вторая, слишком большой кусок, видна в цифрах: суточные окна и
чанки по 512 токенов находят тему, но три четверти того, что они приносят, к ней
не относится.

| Вариант | Векторов | R@10 | MRR | R@1000 ток. | Коротких в top-10 |

Простое исключение коротких сообщений из индекса убирает их из выдачи и экономит

Вывод: само сообщение должно оставаться найденным, но не по собственному
вектору. Короткое сообщение стоит включать в чанк с соседями и находить через
него.

## Другие задачи

Прямых замеров для этих задач нет. Ниже — что из измеренного к ним относится, и
где это предположение.

| Задача | Что подходит | На чём основано |
|---|---|---|
| Тематическая кластеризация, интересы пользователя | сообщения от 10 токенов или мелкие чанки | силуэт тем выше у мелких единиц и отрицателен у крупных; сигнал слабый |
| Поиск характерных высказываний | уровень сообщений | высказывание — это одно сообщение; плотность выдачи 76 % |
| Повторяющиеся темы | уровень сообщений | то же; замера нет |
| Суммаризация | чанки с границей по паузе | чанк должен быть связным отрывком; замера нет |
| Изменение тем со временем | чанки с границей по паузе или сообщения с датой | чанк по бюджету токенов охватывает до десяти суток и для этого не годится |
| Контекст для LLM | сообщения с учётом чанков, затем соседние сообщения из таблицы | R@1000 ток. и плотность выдачи |

Лучшая для поиска нарезка не лучшая для всего. Чанк по бюджету токенов хорош как
второй уровень поиска, но плох для анализа во времени. Поэтому таблицы допускают
несколько наборов чанков одновременно.

   ```
       --params '{"max_tokens": 256, "overlap": 0.1, "same_channel": true}'
   ```
3. **Поиск**: ранжировать сообщения по полусумме собственного сходства и сходства
   лучшего чанка, в который сообщение входит. Очень короткие сообщения тогда
   поднимаются только вместе со своим окружением.
4. **Без приближённого индекса**, оператор `<=>`, поиск внутри пользователя.
5. Для анализа во времени и суммаризации при необходимости построить второй
   набор чанков с границей по паузе, например `hybrid` с паузой 30 минут и тем же
   бюджетом. В поиске он преимущества не показал.

Насколько это обосновано:

- **Надёжно**: уровень сообщений нужен; крупные чанки и окна без ограничения
  размера разбавляют выдачу; короткие сообщения засоряют поиск; приближённый
  индекс при поиске внутри пользователя не нужен.
- **Вероятно**: бюджет 256 лучше 128 и 512 как второй уровень; способ context
  лучше rrf.
- **В пределах шума**: перекрытие 10 % против нуля; граница канала против её
  отсутствия; выбор между базовой и малой моделью.

Что не проверено: способ context реализован только в скрипте замеров, в
приложении его нет; вес 0,5 в нём не подбирался; на запросах, где релевантность
определяется только контекстом, нарезки не сравнивались.

## Как это хранится

Миграция `0004` создаёт таблицы, `0005` задаёт окончательный размер вектора:

- `embedding_models` — имя, ревизия, размерность, объединение токенов,
  нормализация, предел входа, префикс. Ревизия обязательна, поэтому уникальность
  по этим полям не обходится пустым значением.
- `message_embeddings` с ключом `(message_id, model_id)`;
- `chunk_embeddings` с ключом `(chunk_id, model_id)`; удаляются вместе с чанком.

Столбец `vector(384)`. Несколько моделей и ревизий одной размерности хранятся
рядом; модель другой размерности потребует своей миграции. Векторного индекса
нет.

```
python -m scripts.embed --messages
python -m scripts.embed --chunk-set <id>
```

Расчёт не обращается к Telegram, считает только недостающее и не меняет текст
сообщений. `--force` пересчитывает векторы модели заново.

## Как повторить

```
python -m benchmarks.corpus_stats
python -m benchmarks.chunking_benchmark --no-cache --postgres
python -m benchmarks.chunking_benchmark --compare-models
```

Нужны PostgreSQL с собранными комментариями, PyTorch с CUDA и файл
`benchmarks/eval/mapping.local.json`, которого нет в репозитории. Результаты
пишутся в `data/benchmark/results.json` и `models.json`. Повторный запуск на тех
же комментариях дал те же метрики поиска до последнего знака. Быстрая проверка на
выборке: `--sample 300 --only "C tokens 256"`.
